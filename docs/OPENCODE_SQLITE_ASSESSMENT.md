The generated schema and migration-list source files are byte-identical between these two tags (SHA-256 `dc485d31e4d2f4d47f0c0e4243854b04817dc88a42ab9b1bec34b77d9f52ab27` and `0da0d1d3876a39542c2cd2fc0c95cfd182230442b45e174467d503f91043caa8`). A fresh database gets every migration marker after `schema.up`; an existing database may use a legacy Drizzle journal before conversion. The marker alone does not certify which application version or usage writer produced a row ([migration application](https://github.com/anomalyco/opencode/blob/aec0b9a6d8898f68f923aaf08b7306d931fd9d76/packages/core/src/database/migration.ts)).

The schema has a session ID, project ID, parent ID, directory, version, created/updated times, and session-wide token totals. Legacy `message` and `part` rows and newer `session_message` rows retain message IDs and JSON data; `session_message` has a unique `(session_id, seq)` index. These are enough to propose identity and ordering, but session-wide totals cannot replace dated, model-attributed usage facts. The two generations can coexist; counting both would double-count. The `event` table also retains already-normalized events rather than raw provider usage. See the [table definitions](https://github.com/anomalyco/opencode/blob/aec0b9a6d8898f68f923aaf08b7306d931fd9d76/packages/core/src/session/sql.ts) and [projection](https://github.com/anomalyco/opencode/blob/aec0b9a6d8898f68f923aaf08b7306d931fd9d76/packages/core/src/session/projector.ts).

## Accounting decision

The legacy usage normalizer subtracts cache read/write from inclusive input and reasoning from inclusive output. For a valid, complete legacy event, the candidate Odometer mapping is therefore `input + cache.read + cache.write` and `output + reasoning`. But it also replaces absent, nonfinite, and negative provider fields with zero ([legacy normalizer](https://github.com/anomalyco/opencode/blob/aec0b9a6d8898f68f923aaf08b7306d931fd9d76/packages/opencode/src/session/session.ts)). The newer runner likewise calls `safe(usage?.field)` for each field and saves a zero-valued settlement even when `event.usage` is absent ([runner normalizer](https://github.com/anomalyco/opencode/blob/aec0b9a6d8898f68f923aaf08b7306d931fd9d76/packages/core/src/session/runner/publish-llm-event.ts), [event publication](https://github.com/anomalyco/opencode/blob/aec0b9a6d8898f68f923aaf08b7306d931fd9d76/packages/core/src/session/runner/llm.ts), [assistant projection](https://github.com/anomalyco/opencode/blob/aec0b9a6d8898f68f923aaf08b7306d931fd9d76/packages/core/src/session/message-updater.ts)). The projection records completion, finish, cost, and tokens, but no raw-usage-present bit.

Consequently, two upstream inputs—an absent usage object and an explicit object with every usage field zero—can produce the same completed assistant row and event. Completion and zero cost do not distinguish them. A read-only SQLite adapter cannot recover that erased provenance. Nonzero fields prove some observed usage, but do not prove that *all* token subsets were reported; a missing cache or reasoning field is also normalized to zero. The session total is accumulated from the same normalized facts, so it cannot repair the gap. No provider path reviewed here has an independent golden request-usage oracle that establishes completeness for v1.18.33 and v1.18.34.

The required evidence gate therefore fails for complete event-level accounting. **Do not register an OpenCode provider or ingest these rows as complete token/cost facts.** Treat zero or incomplete usage as unavailable, not measured zero. The tempting alternative of importing only nonzero rows would make date/project totals partial while looking complete.

## Reproducible structural fixture and limits

For each pinned commit above, [the local structural check](../scripts/verify-opencode-sqlite-schema.py) verifies the downloaded `schema.gen.ts` SHA-256 and extracts its `session`, `message`, and `session_message` `CREATE TABLE` statements into a temporary SQLite database. Run it with the v1.18.33 and v1.18.34 `schema.gen.ts` paths in that order. Synthetic rows use one project/session, a parent ID, two assistant IDs, distinct model/provider metadata, ordered `seq` values, and one zero and one nonzero token object. A read-only `mode=ro` connection selects the intended IDs/timestamps/numeric JSON fields. Both releases accepted the same rows because the DDL is identical. A duplicate `(session_id, seq)` was rejected by the source index. This proves only table compatibility and that a bounded SQL reader can avoid prompt/body selection; it is **not** an upstream-generated golden request fixture and cannot prove usage presence, provider-specific accounting, resume behavior, or long-term compatibility.

A future adapter needs a pinned upstream change or independent per-request record that preserves raw usage presence and subset completeness, followed by golden provider-path fixtures from two releases. Then validate exclusive legacy/new projection selection, model switches, resumes, rollback/deletion, active WAL and locks, corrupt/missing files, unknown migrations, Odometer whole-hour and edge rollups, and native read-only behavior. Read only local metadata and numeric usage; never open auth files or message bodies. Keep Kilo Code on its own version/migration track.
