# Quota sources, accounts, and budgets

Open Analytics to see transcript quota observations, soft budgets, and the **Live account quotas** disclosure. All live polling and notifications ship off.

## Consented Codex account polling

1. **Allow one account lookup** authorizes the installed native `codex` executable to identify its signed-in account using `account/read` and `account/rateLimits/read`. This is a credential-using action, explicitly separate from periodic polling.
2. Check the returned opaque account ID, choose a local label, and **Enable polling for this account**.
3. Odometer reads at most once every five minutes; errors back off to at most hourly retries. One installed CLI has one current account, so enabling an account pauses the other approved accounts. Their views remain distinct.
4. Pause or revoke in the same disclosure. Revocation removes persisted consent and clears the reading immediately. Late in-flight results are discarded. An already-started request can finish, but cannot republish data after revocation. Other running instances recheck the bounded consent file before polling, before accepting a response, and on status reads. Saved changes use a cross-process lock and compare the previously observed consent; a stale save cannot restore consent that another instance revoked. If a revoke cannot be saved, polling stays paused in that instance across external settings changes until an explicit local enable or approval, and the error reports that durable revocation failed.

The native CLI is resolved from absolute PATH directories. Shell shims are not executed. A CLI missing reliable local `workspaceRouting.chatgptAccountId` cannot poll automatically: it is **unsupported**. Each periodic read checks the local account ID before requesting quota, then checks the account ID in the quota response. A different account never inherits approval. No login, token refresh, private HTTP endpoint, or credential-file parsing is implemented by Odometer. The native CLI owns its own authentication behavior.

Only account ID, local label, approval time, and enabled state enter `quota-live-v1.json`. Credentials, emails, provider response bodies, and quota readings are not stored in Odometer. Readings stay in memory and never enter usage history, exports, diagnostics, or performance recordings. CLI stderr is discarded; failures are fixed codes. Requests have a 15-second deadline and bounded input, message count, and response bytes; the direct child is killed and reaped. The bounded pipe reader is detached during teardown so an inherited pipe cannot hang the app; a four-reader budget prevents stuck descendants from accumulating unbounded reader threads.

The dashboard and tray use the same account/bucket snapshots and backend window conversion. The backend event `live-quota-updated` carries no payload and invalidates the tray. Each bucket retains its identity. Provider-reported usage permission and spend controls remain separate from percentages: remaining window percentage does not establish permission to use a model. Unknown, offline, expired-auth, changed-account, and unsupported states do not display invented zeroes. Readings older than ten minutes or past their reported reset are stale. Clock rollback makes affected numeric windows unavailable; a fresh read is needed after sleep or a failed refresh.

The live reader does not infer a previous reset or forecast from one observation. Transcript views show counter-decrease observation time separately from an actual reset, which these sources do not report. A decrease can be rolling-window decay; both that forecast anchor and a start inferred from the next reset schedule remain estimated, with medium confidence at most. `window_start_basis` distinguishes `counter_decrease`, `reset_schedule_estimate`, and `unknown`; it never establishes a previous reset. Pace/forecast amounts remain estimates. Current transcript records do not establish account identity, so historical usage remains **unattributed** even when a live account is approved.

## Soft project budgets

Budgets are advisory. Choose provider scope or a project, token or USD API-estimate units, rolling hours, and a threshold. Edit, pause, or remove budgets in place. Account-wide percent budgets use **unattributed transcript observations**; they are not silently rebound to a newly approved live account. Exact cached live-account alert rules are described below.

Token and monetary budgets query the durable ledger, including retained sessions, explicit project assignments, canonical project merges, full-hour rollups, and inclusive partial-hour boundaries. Future-dated events are excluded. After a confirmed purge, a budget window can be shown only when its inclusive start is strictly after the recorded upper timestamp of all deleted accounting events and that record still matches the purge tombstones. Earlier purges without this bound, recovery, stale ledger data, or a concurrent purge leave the budget unavailable; global history coverage remains incomplete. Missing history, unknown projects, unbucketed tokens, missing rates, and non-USD plan rates are unavailable, not free headroom. Monetary amounts use the shared current Rust API-estimate surface for Codex and the USD plan surface for other providers. These are base-rate estimates, not invoices, subscription allowance, or a guarantee that request-size premiums are included.

An older archive can retain two keys for one transcript if its first turn appeared after a token event. New observations reconcile that same-source continuation without adding another key. For existing archives, token and USD budgets with a selected source/artifact mismatch or overlapping identical token events under a superseded sibling show **Historical identity is ambiguous** instead of a doubled value. If the bounded identity check cannot finish, those budgets show **Historical identity could not be verified**. The shared report guard also withholds affected table, chart, tray, widget, workflow, and summary-export aggregates; unchanged cached rows are part of the proof. Individual source inspection remains available. A scope or date window whose accounting can be proved remains usable, and cumulative category proof is separate from date-window proof. No records are removed or merged automatically. A routine rescan does not prove that an already duplicated archive was repaired; preserve the archive for a separately reviewed repair.

Notifications require opt-in. Quiet hours and already-crossed thresholds remain deduplicated, and stale quota observations do not trigger a fresh crossing. Concurrent evaluations are serialized; stale settings edits cannot overwrite a newer revision. Notifications are suppressed when deduplication cannot be persisted. Settings live in `quota-v3.json`; absent-only v2/v1 migration preserves older files for older releases. Invalid or newer settings fail closed instead of being replaced with defaults.

### Exact approved-account threshold alerts

The **Approved account quota alerts** editor adds independent percent-used rules for an exact approved Codex account, its consent timestamp, model limit ID, window kind, and reported duration. New rules start disabled. Enable each rule explicitly and enable **Shared alerts**; the same master switch and local quiet hours govern all delivery. This editor and the alert collector read only cached observations. They start no account lookup, credential access, or provider request.

A fresh, unambiguous live-provider reading can cross a threshold once. An observed reading below it rearms the rule. Missing, expired, future, changed-consent, duplicate, or mismatched observations remain unavailable and never resolve an armed crossing. Startup, resume, policy changes, disabled delivery, and quiet observations are consumed without backlog. Still-configured armed live keys survive notification-history pruning (at most 32 rules); removing or changing a rule clears its old key. Notices contain fixed labels and typed local evidence routes, never account identifiers, account labels, provider bodies, or credentials.

`quota-v3.json` is authoritative. Only an absent v3 permits read-only migration from v2, then v1. Migration preserves transcript token/USD budgets, master/quiet/ambient settings and dedup/recent metadata. Corrupt, unreadable, oversized, or newer v3 files fail closed and are preserved. Older releases can continue writing their v2 file without overwriting v3 account rules. The next successful configuration or collector write persists v3. Transcript pricing and ledger totals remain unchanged and cannot be attributed to an inferred live account.
