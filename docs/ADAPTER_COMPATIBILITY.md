# Additional agent adapter evidence

Reviewed 2026-10-04. This is a source-format comparison, not a support promise. **Observed** means the cited official docs or pinned source declares the field; **inferred** means it follows from source structure or storage behavior but is not a stable public contract; **estimated** means it cannot be mapped as a measured value; **unavailable** means this review found no sufficient evidence. These labels describe evidence, not confidence in an undocumented runtime implementation.

Odometer’s usage convention is inclusive input (cached reads and cache creation are subsets of input), and reasoning output is a subset of output. A source that only publishes session totals cannot provide event-time/model attribution or date-range accounting. Missing usage must remain unavailable, never become a measured zero.

## Recommendation

Evaluate **OpenCode v1.18.34 SQLite only** as the first bounded adapter candidate, with implementation deferred until golden synthetic fixtures prove the observed mapping (`input + cache.read + cache.write`; `output + reasoning`) for supported provider paths and at least one adjacent release. Because its normalizer erases missing/invalid-vs-zero provenance, the fixtures and source trace must also establish a reliable usage-presence/completion signal; otherwise ambiguous zero-valued usage must be unavailable. Define read-only behavior for active/WAL databases, migrations, corrupt files, deletion, and unknown schemas. Limit extraction to metadata and numeric usage; never read auth files or message content. If fixtures cannot establish a safe accounting and compatibility boundary, defer it rather than falling back to token estimation.

This recommendation is for a candidate, not approval to ship an adapter. It needs a separate implementation review under Odometer’s filesystem and privacy boundaries. No network or credential access is proposed.

This supersedes the earlier README assessment in [commit `7ee32a2`](https://github.com/ekalb81/agent-odometer/commit/7ee32a2), which described OpenCode as scattering a session across many files. The release reviewed here stores session and message records in SQLite; schema stability and accounting semantics remain open questions.

## Bounded follow-up scope

If the candidate is accepted, limit the follow-up to OpenCode’s user-selected/local default data root and a read-only SQLite adapter for explicitly supported database schema versions. Read only session and assistant-message metadata/usage needed for session ID, project directory, parent ID, model/provider, timestamps, and numeric token fields. Do not read `auth.json`, prompts, responses, tool bodies, or network endpoints. Treat unsupported schema versions, missing or ambiguous zero-valued usage, inaccessible/locked databases, and unverified subset mappings as unavailable with a clear source status; never fall back to estimates or zeros. Prove cache/reasoning mapping and usage-presence/completion evidence against golden synthetic DB fixtures from v1.18.34 and an adjacent release, reconcile event totals to the current Odometer oracle, and verify read-only behavior with a live/WAL-shaped fixture before supporting a version. No parser implementation is part of this discovery change.
